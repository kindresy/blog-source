## 实现行为

每轮先发送 COUNT 包基线，再发送 COUNT 包负载数据。单包 20～260 字节，每批最多 16 包；使用 run/generation/sequence/length/stage/version、变化的数据和 CRC32 逐包检查，批次之间通过 IBI 和显式控制帧同步。Host 保持一个在途同步 ioctl，包间不逐包等待 IBI。

负载阶段 Host 启动一个 CRC/内存计算子进程并在退出时回收；Target 在服务 RX 的迭代之间执行指定次数的 CRC/内存工作，不关闭中断。它是可复现的附加软件负载，不代表已经运行实际产品应用。记录分阶段耗时、队列高水位、RX 服务间隔及实际工作量。

`recover` 模式注入一个完整、内容正确但 CRC 翻转一位的包。Target 保存证据，Host 显式停止数据提交并请求恢复；确认队列空和身份未变后，验证四字节短写与逐包握手的 16 包长写，再读取带 CRC 的统计结果。此恢复不复位、不清 FIFO、不重新枚举。

**只覆盖应用 CRC 异常恢复。** HALT、溢出、坏分片、超时、DA 变化等硬件/协议异常保留现场并返回失败，硬件故障恢复为 NOT_TESTED。没有自然故障的压力运行不会自动算作恢复通过。

首次小规模验证的 Target 命令：

```text
i3c_test long-write run 256 31 1 recover
```

收到本次 READY 后，Host 在新 APP 所在目录设置真实 node 与 generation，再执行：

```sh
./i3c-host -d "$node" auto long-write "$generation" 256 31 60000 recover
```

执行前仍须按操作文档完成双方初始化、枚举与状态确认；这些命令尚未在板端执行。通过后再以新会话扩大到每阶段 1000/10000 包。
