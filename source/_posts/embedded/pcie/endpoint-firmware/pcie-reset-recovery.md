一张多功能卡上，Function 0 的队列卡住了，Function 1 还在处理业务。Host 若能只复位 Function 0，固件就不能顺手把全卡共享的引擎也清掉。反过来，如果整条链路已经丢失，只重新初始化一个队列也恢复不了访问。恢复流程首先要回答两个问题：**谁受了影响，现在还可以通过什么路径访问设备？**

## 看事件的作用域

| 观察到的事件或操作 | 哪些对象要考虑 | 首先核对什么 |
|---|---|---|
| Link Down | 经过这条链路的所有下游事务 | 链路何时丢失、上游报告了什么、哪些请求仍在途 |
| 链路重训 | 该链路的两端以及等待它恢复的访问 | 训练是否成功，配置访问何时恢复 |
| Hot Reset / Secondary Bus Reset | 对应桥下游的设备和功能 | 受影响的子树、哪些其他驱动也需要参与 |
| FLR（Function Level Reset） | 指定 Function 及其私有状态 | 是否声明支持 FLR，哪些队列和上下文属于它 |
| Fundamental Reset | 相应硬件复位域内的组件 | 平台怎样提供复位，功能状态和链路如何重新建立 |
| 热拔或永久失联 | 被移除设备及其驱动持有的资源 | 通知上层终止业务，防止继续提交或等待设备 |

Link Down 是链路状态的观察结果。掉电、拔卡、主动复位或链路故障都可能造成这个结果。仅凭一条 Link Down 日志推断“某个队列头已经清零”，依据不够。重训恢复了物理链路，同样不能说明复位之前的命令已成功完成。

## FLR 时，固件应该重建谁的状态

Host 对支持 FLR 的 Function 启动复位，目的在于让该功能恢复到可以重新配置的状态。Endpoint 固件通常需要有一个按 Function 索引的状态视图，至少能指出提交队列、完成队列、门铃状态和中断来源归谁。对于多个功能共用的执行单元，设计上还要能分别停止接收目标功能的新命令、隔离旧工作产生的迟到完成。

假设功能 0 复位前，队列槽 6 里有一笔写回。复位后驱动重新设置环基址、又用到槽 6。若旧任务的完成还能按旧索引写进新环，即使链路上每个包都传对了，应用看到的也会是一次假的完成。设备可以在启动新队列前排空旧任务，或按硬件设计采用能够区分队列世代的机制。判断恢复成功，要在业务边界检查旧工作确实不能污染新队列。

Linux 的 `pci_reset_function()` 会在适用的条件下对功能执行复位，并围绕复位保存、恢复 PCI 状态。它可能使用该设备支持的不同复位方法。驱动自己的描述符、队列语义、重提策略仍由功能驱动和设备协议处理。[Linux PCI reset 接口](https://docs.kernel.org/6.12/driver-api/pci/pci.html)

## 一条链路断开时，恢复的单位扩大了

链路断开后，Host 对下游的正常配置读或 MMIO 可能无法完成。以“等设备寄存器某一位变回 0”为唯一退出条件的等待在这里尤其危险。Host 侧应阻止新业务进入，给未完成请求留下可解释的结束状态；EP 侧若能从本地观察链路，也应记录仍在途的工作。对于已经发出、结果不明的写，业务层需要先判断是否能安全重试。

Hot Reset 会影响下游的多个功能。恢复时要同时考虑共享资源和每个功能的私有资源。若有多个驱动实例，公共初始化应由约定的执行者完成，随后再由各实例恢复自己的队列和中断来源。Linux 的 PCI 错误恢复文档专门讨论了多功能卡上这一点。[Linux PCI Error Recovery](https://docs.kernel.org/6.12/PCI/pci-error-recovery.html)

## Host 回调和设备固件怎样对上

Linux 6.12 的 PCI 错误恢复接口允许驱动通过 `struct pci_error_handlers` 反馈恢复条件。典型流程会依严重程度、平台和驱动返回值分支。[PCI 错误恢复阶段](https://docs.kernel.org/6.12/PCI/pci-error-recovery.html) [PCIe AER 驱动指南](https://docs.kernel.org/6.12/PCI/pcieaer-howto.html)

- **`error_detected()`** 收到通道状态，先停上层提交并判断是否需要复位。通道已冻结时，应避免依赖常规 MMIO 去确认停机。
- **`mmio_enabled()` 或 `slot_reset()`** 在对应条件满足后进入。驱动可以检查恢复的访问条件、重新设置设备；Endpoint 此时应能按其接口约定接受初始化。
- **`resume()`** 代表平台允许恢复正常业务。适合此时开放队列，并验证一次新请求能取走、写回且只完成一次。

故障记录里最值得留下的是四个时间点：最后一笔已确认完成的命令、停止新提交、首次重新读到可靠的设备状态、第一笔重新完成的业务。它们能区分“Link 已回来”“Host 已可访问设备”和“数据面已恢复”这三个结论。
